# Ohnix Desktop (Tauri shell)

Fase B de `docs/architecture/ohnix-multiplatform-strategy.md` §25: envuelve el build existente de `Frontend/` en una ventana nativa Tauri v2, sin tocar la SPA React. No hay UI nueva ni lógica de negocio nueva aquí - solo configuración de empaquetado y la superficie mínima de integración nativa que una SPA en un webview necesita.

## Decisiones tomadas en esta fase

- **La ventana de producción carga la URL en vivo (`https://ohnix.co/login`), no una copia empaquetada.** Decisión revisada tras armar también Mobile (Fase D, WebView) y que el usuario preguntara explícitamente por consistencia entre las 3 plataformas: apuntar a la URL real en vez de bundlear `Frontend/dist` dentro del instalador da **dos cosas a la vez que un bundle local no puede dar juntas** - (1) Desktop corre siempre el código más reciente sin necesitar una recompilación/relanzamiento cada vez que cambia el sitio, igual que Mobile, y (2) sigue funcionando sin internet y sincronizando solo al recuperar conexión, porque esto se apoya en la infraestructura de offline-first que la app web *ya tiene* (Service Worker instalable + espejo Dexie + outbox, ver `OFFLINE_ARCHITECTURE.md`) - un Service Worker registrado contra `https://ohnix.co` es un contexto seguro real y funciona exactamente igual que en un navegador normal, cosa que **no** estaba garantizada contra el origen sintético `tauri://localhost` que usaba el bundle local. No es una apuesta nueva, es reutilizar sin cambios un sistema ya construido y probado.
  - `frontendDist`/`beforeBuildCommand` siguen apuntando al build local de `Frontend/` porque Tauri exige que el valor exista para empaquetar (íconos, metadata) - ya no es lo que la ventana principal realmente carga en producción. Limpiar esa dependencia residual es un ítem de pulido futuro, no bloqueante.
  - En **dev** (`tauri dev`) la ventana sigue apuntando al Frontend local (`http://localhost:3000/app.html`, ver `devUrl`) a propósito - se quiere seguir iterando contra cambios sin deployar. Solo el build de **producción** (`app.windows[0].url`) apunta a la URL en vivo.
  - Se usa `/login` y no `/app.html` como el path de producción, igual que Mobile - evita depender de que la normalización de `/app.html` (ver más abajo) ya esté deployada en `ohnix.co` en el momento en que alguien instale Desktop.
- **`beforeBuildCommand`/`beforeDevCommand` reutilizan `Frontend/package.json` tal cual** (`npm run build`/`npm run dev --prefix ../Frontend`) - incluye `generate-seo-files.js`/`prerender.js`, que son irrelevantes para `app.html` pero inofensivos de correr (no tocan ese archivo). Optimizar eso a un build más liviano específico de Desktop es un ítem futuro opcional, no un requisito de esta fase.
- **CSP explícito en `tauri.conf.json`** (`app.security.csp`) en vez de dejarlo `null`: whitelist de `connect-src` para el backend real (`https://ohnix.onrender.com` prod, `http://localhost:3001` dev) y sus contrapartes de socket (`wss://`/`ws://`), más `http://localhost:3000`/`ws://localhost:3000` para `tauri dev`. Es seguro incluir las entradas de localhost en el build de producción empaquetado también - simplemente nunca se alcanzan fuera de dev.
- **Puerto de dev 3000, no el 5173 por defecto de Vite**: dos razones. (1) El Frontend normal del repo (otro worktree/terminal) suele tener su propio `vite` corriendo en 5173 - usar el mismo puerto para el dev server de Desktop chocaría (`--strictPort` fallaría en vez de saltar a otro puerto silenciosamente, que rompería el `devUrl` fijo). (2) Más importante: `Backend/utils/allowedOrigins.js` tiene una whitelist de CORS hardcodeada para desarrollo local (`http://localhost:3000`, `http://localhost:5173`) - cualquier otro puerto (se probó con 5183) es rechazado por CORS y el login falla con un error genérico de red, sin mensaje claro. 3000 ya está en esa whitelist, así que Desktop funciona contra un backend local sin tocar ni reiniciar el backend.
- **`/app.html` no es una ruta válida para React Router (relevante solo en dev ahora)** - en Web, `vercel.json` reescribe cualquier path no-marketing a `/app.html` **sin cambiar la barra de direcciones**, así que `BrowserRouter` siempre ve el path real (`/login`, `/dashboard`, etc.). La ventana de Tauri en modo dev no tiene barra de direcciones ni ese rewrite: pide literalmente `/app.html`, que no matchea ninguna `<Route>` y cae al 404. Se normaliza en `Frontend/src/main.jsx` con un `history.replaceState` a `/login` antes de que `BrowserRouter` monte (ver el comentario ahí) - `/login` es seguro como default porque `GuestRoute` ya redirige a `/dashboard` si hay sesión activa. En producción esto ya ni aplica, porque la ventana apunta directo a `/login` (ver arriba), nunca a `/app.html`.
  - `style-src` incluye `'unsafe-inline'` **deliberadamente**: antd/`@ant-design/cssinjs` inyecta `<style>` en tiempo de ejecución vía DOM APIs, no vía un `<link>`/`<style>` que Tauri pueda nonce-ar automáticamente en el build. Sin esto, la app no renderiza nada de antd. Es el mismo tradeoff que ya existe implícitamente hoy en el navegador (sin CSP en absoluto en Web) - no es un endurecimiento nuevo que se esté evitando, es paridad. Si se quiere cerrar esto más adelante, la ruta es configurar antd's `StyleProvider`/`@ant-design/cssinjs` para nonce-ar sus tags (soportado, no evaluado en esta fase).
- **Socket.IO sin cambios** (`Frontend/src/live/socketClient.js` sigue usando `socket.io-client` plano) - el documento de estrategia (§6) advierte no enrutar Socket.IO por `@tauri-apps/plugin-websocket` por una condición de carrera real y reproducida. Nada que hacer aquí, solo confirmar que el CSP de arriba permite la conexión.
- **Rutas de assets de Vite**: `base` no está seteado en `vite.config.js` (default `/`), lo cual ya funciona correctamente contra el origen sintético de Tauri (`tauri://localhost` / `http://tauri.localhost`) - no requirió ningún cambio, contrario a lo que §6 marca como el problema más comúnmente reportado en otros proyectos.
- **Capability por defecto es default-deny** (`capabilities/default.json`): solo `core:default`, nada de filesystem/shell/hardware. Los plugins de impresora térmica/cajón de dinero son Fase C (§17) - se agregan como una entrada de capability con scope explícito cuando ese trabajo empiece, no de forma especulativa ahora.
- **Almacenamiento local: Dexie/IndexedDB sin cambios** - funciona sin modificación en el webview de Tauri (§11), así que Fase B no depende de ni usa `packages/sync-core` (Fase A) en absoluto. Las dos fases son independientes; el orden A→B en el roadmap es una preferencia de secuenciación, no una dependencia técnica dura.
- **Iconos**: generados con `tauri icon Frontend/public/ohnix-icon-v2-512.png` (comando oficial). Se eliminaron `icons/ios/` y `icons/android/` que el comando genera por defecto - Tauri Mobile no está en el alcance de este documento (Mobile es React Native + Expo, §7-8), así que esos assets no tienen consumidor.

## Verificado end-to-end (Windows)

- **`tauri dev`**: la ventana nativa abre, carga `app.html`, `BrowserRouter` resuelve a `/login` (no al 404 que daba antes de la normalización de path de arriba). Login real contra un backend local (`localhost:3001`) funciona: CORS, CSP `connect-src`, y el flujo de auth completo (JWT bearer + cookie) de punta a punta.
- **`tauri build` (release real)**: probado - el `.exe`/instalador de producción carga `https://ohnix.co/login` en vivo correctamente, con sesión ya autenticada persistida (misma cookie/token que la web). Genera tanto `.msi` como `-setup.exe` (NSIS) - ver `target/release/bundle/{msi,nsis}/`.
- `cargo check`/`cargo run` compilan limpio con el Windows SDK instalado (ver nota de toolchain abajo si esto falla en otra máquina).

## Fase C (§17, §25) - solo la parte sin hardware

Fase C completa (piloto de impresora térmica/cajón de dinero) necesita una tienda real y un modelo de impresora real para validar - no hay eso disponible en esta máquina de desarrollo, así que no se tocó (agregar un plugin de impresora sin poder probarlo contra hardware real sería exactamente la apuesta especulativa que el documento de estrategia dice evitar).

Lo que sí quedó verificado, y no necesita ningún trabajo adicional:

- **Lector de código de barras USB/Bluetooth (HID)**: estos dispositivos se comportan como un teclado - el sistema operativo y el webview los ven como eventos de teclado normales, indistinguibles de tipear a mano. `main.rs`/`capabilities/default.json` no interceptan teclado de ninguna forma (sin plugin de global-shortcut, sin comando nativo alguno), así que no hay nada en la capa de Tauri que pueda bloquear o alterar esos eventos. El login (`Frontend/src/components/auth/...`, un `<Input>` de antd normal) ya probó que tipear en un campo de texto dentro del webview de Tauri funciona igual que en un navegador - el campo `product_code` de `ProductModal.jsx` (que ya tiene el hint "puedes usar un lector de código de barras USB o Bluetooth: solo haz clic en este campo y escanea") es exactamente el mismo tipo de input, así que funciona por el mismo mecanismo, sin necesitar una prueba aparte con hardware real. Si en el futuro aparece un caso donde el scanner emula algo distinto a teclado (raro, pero existe en el mercado - lectores seriales/USB-CDC crudos), esa es la única variante que sí necesitaría el `tauri-plugin-serialplugin` que menciona el §17.

## Auto-actualización (plugin `updater`)

Agregado además de lo mínimo de esta fase, a pedido explícito - **esto es para el binario nativo en sí** (permisos, ícono, ventana, futuros plugins de hardware de Fase C), nunca para el contenido de `ohnix.co`, que ya se actualiza solo cada vez que la ventana carga la URL en vivo (ver arriba). El chequeo corre 100% en Rust (`src/main.rs`, función `check_for_update`) al arrancar la app - nunca toca ni depende del JS de la página cargada, así la ventana sigue mostrando exactamente lo mismo que un navegador vería.

**Cómo funciona**: al arrancar, la app pregunta a `https://github.com/AleRxJ/Ohnix/releases/latest/download/latest.json` (configurado en `tauri.conf.json`'s `plugins.updater.endpoints`) si hay una versión más nueva que la instalada. Si la hay, muestra un diálogo nativo del sistema operativo (no una página web) preguntando si instalar - si el usuario acepta, descarga, instala, y reinicia la app sola.

**La clave de firma** (`src-tauri/updater-signing-key.pem` + su contraseña en `src-tauri/.updater-key-password.txt`) se generó con `npx tauri signer generate` y **nunca se commitea** (ver `.gitignore`) - son las credenciales que le prueban a una instalación existente que una actualización realmente viene de vos y no de alguien más. Guardalas en un gestor de contraseñas antes de que se pierdan de esta máquina - si se pierden, no hay forma de firmar actualizaciones futuras que las instalaciones ya existentes acepten (habría que rotar la clave pública en `tauri.conf.json` y todos tendrían que reinstalar a mano una vez).

**Para que el workflow de CI (`desktop-build.yml`) pueda firmar los builds**, hay que cargar esas dos credenciales como secretos del repositorio (Settings → Secrets and variables → Actions → New repository secret):
- `TAURI_SIGNING_PRIVATE_KEY`: el contenido completo de `updater-signing-key.pem`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: el contenido de `.updater-key-password.txt`

**Para publicar una actualización real**: subí el número de `version` en `tauri.conf.json`, empujá el cambio (dispara el workflow), y cuando termine and publicá el Release en borrador que deja en GitHub - a partir de ahí, cualquier instalación existente que abra la app va a ver el diálogo de actualización.

**No probado todavía**: el flujo completo de extremo a extremo (generar un release real vía CI, instalarlo, subir la versión, confirmar que una instalación vieja detecta y aplica la actualización sola) - el código compila limpio (`cargo check`) pero esto necesita un ciclo real de release para verificarse.

## Cómo correr

```
npm install         # una vez, en la raíz - instala @tauri-apps/cli
npm run dev:desktop # abre la ventana nativa contra Frontend en modo dev (localhost:3000/app.html)
npm run build:desktop
```

Requiere el toolchain nativo de Tauri instalado (Rust, y en Windows el WebView2 Runtime - ya viene preinstalado en Windows 11) **y el Windows SDK completo** (`Windows Kits\10\Lib\...\kernel32.lib`) - si `cargo check` falla con `LNK1181: cannot open input file 'kernel32.lib'`, repará la instalación de Visual Studio Build Tools desde el Visual Studio Installer (botón "Repair"), no reinstales Rust.
